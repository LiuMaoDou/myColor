## 00. 项目摘要与默认决策

**一句话定位：一个能够输入、预览、复制、分类、收藏、发布和复用颜色资产的个人工作台，并逐步扩展为颜色资源中心。**

最重要的使用路径：

```text
输入颜色或粘贴一组颜色
→ 自动识别格式并即时显示色块
→ 显示当前格式的颜色值
→ 点击色块复制这个颜色值
→ 添加名称、分类、标签和来源
→ 保存为单色或色板
→ 私人使用，或主动发布到公开分类页
```

网站收藏走另一条同样简短的路径：

```text
粘贴网址 → 填写名称和简介 → 分类/标签 → 保存 → 访问、搜索和整理
```

### 默认决策

| 事项 | 本计划采用的方案 |
|---|---|
| 产品形态 | 响应式 Web 应用，桌面优先，同时保证手机可用 |
| 首要用户 | 站长本人；兼顾设计、开发、教学、PPT 和科研图表使用场景 |
| 首版账号 | 一名站长账号，关闭开放注册；数据结构保留用户归属，不预先建设团队系统 |
| “分类发”的含义 | 同时支持分类保存，以及主动发布到公开分类页 |
| 默认可见性 | 新内容为私有草稿；不得自动公开 |
| 首版核心资源 | 单色、色板、颜色网站书签 |
| 后续资源 | 渐变、图片灵感、教程/文章、设计令牌、相关工具 |
| 首版数据存储 | PostgreSQL 持久化；浏览器存储只保存偏好和临时草稿 |
| 技术方向 | Next.js + TypeScript + Tailwind CSS + shadcn/ui + Supabase + Culori |
| 首版不做 | 开放社区、评论、交易、全网抓取、团队协作、专业印刷色管理 |
| 扩展原则 | 新增资源类型和工具模块，不用“一个页面塞所有功能”的方式扩张 |

**成功标准：用户不必先学习色彩模型，就能把一个颜色可靠地存下来；需要专业格式时，也不会丢失透明度、来源或颜色精度。**

## 01. 用户需求与功能对应

| 用户需求 | 产品实现 | 首版验收要点 |
|---|---|---|
| 输入颜色，支持多种格式 | 统一颜色输入框、格式识别和结构化输入 | HEX、RGB/RGBA、HSL/HSLA、HSV/HSB、CSS 英文色名可用 |
| 输入后显示颜色块 | 输入过程中实时解析，合法后显示色块 | 不必点保存，也不必请求服务器 |
| 色块显示颜色和值 | 色块配固定色值信息区，提供格式切换 | 手机端不依赖悬停才能看到色值 |
| 点击复制颜色值 | 色块为复制按钮，值与所见格式一致 | 成功后提示，失败时提供可选择文本 |
| 可以分类 | 分类树、标签、合集三套机制 | 支持编辑分类和批量归类 |
| 可以分类发布 | 私有草稿与公开发布分离 | 公开列表不泄露草稿、私有笔记或私有附件 |
| 收藏颜色网站 | 网址卡片、名称、简介、分类、标签和来源 | 手动录入始终可用，不依赖网页抓取成功 |
| 颜色相关内容都能逐步加入 | 统一资源模型 + 分类型编辑器 + 工具页 | 新增渐变/图片时不推翻收藏、搜索、权限系统 |
| 延续前面整理的内容 | 导入已有 12 套配色与 15 个网站 | 保留场景、颜色角色、网址和来源说明 |

### 优先级定义

- **P0：首版上线必须完成。** 未完成不能宣称核心功能已交付。
- **P1：第二阶段增强。** 原始数据结构预留，但不阻塞 P0 上线。
- **P2：成熟阶段扩展。** 有实际使用需求后再实施，不提前堆砌。

## 03. 资源类型与信息架构

### 3.1 统一资源类型

| 类型 | 标识 | 主要内容 | 上线阶段 |
|---|---|---|---|
| 单色 | `color` | 一个颜色、原始输入、颜色值、名称、来源 | P0 |
| 色板 | `palette` | 有顺序的多个颜色、角色、用途、说明 | P0 |
| 网站 | `website` | URL、标题、简介、分类、工具能力标签 | P0 |
| 渐变 | `gradient` | 渐变类型、角度、色标、位置、插值空间 | P1 |
| 图片灵感 | `image` | 图片、版权/来源、提取颜色、备注 | P1 |
| 文章/笔记 | `article` | 自写笔记或外链摘要、关联颜色、来源 | P1 |
| 设计令牌 | `token_set` | 命名颜色、语义角色、主题、导出配置 | P2 |

颜色工具不是必须收藏的“内容类型”。例如对比度检测是工具页，检测后可以把配色或报告摘要保存到现有资源。

### 3.2 分类、标签、合集的区别

| 机制 | 回答的问题 | 示例 | 规则 |
|---|---|---|---|
| 分类 | 这是什么用途的资源？ | 学术汇报 / 教育教学 / 科技商务 | 层级结构，首版最多三级 |
| 标签 | 这项资源有哪些属性？ | 低饱和、蓝绿、温暖、免费、图表 | 扁平、多选，支持批量修改 |
| 合集 | 哪些资源一起服务于一个项目？ | 数学心态课题汇报、个人网站改版 | 跨资源类型，自定义排序 |

分类可多选，并可指定一个主分类用于面包屑；未归类内容进入虚拟“未分类”视图。单项收藏可同时出现在多个合集，不复制底层数据。

### 3.3 建议的初始分类

```text
学术与教育
  学术汇报
  教育教学
  科研图表
科技与商务
  科技 / AI
  商务汇报
  产品界面
设计风格
  极简
  传统文化
  柔和 / 低饱和
颜色工具与知识
  配色生成
  图片取色
  可访问性
  色彩理论
```

这些只是可修改的初始数据，不把“学术”等类别写死在程序中。资源类型是单独筛选项，不再把“网站”“色板”重复当成分类层级。

### 3.4 搜索与组织的共同规则

类型、分类、标签、可见性、收藏状态、时间可组合筛选；筛选条件进入 URL 查询参数，刷新与后退不丢失。名称、分类、标签均支持中文。

## 04. 页面与核心交互设计

### 4.1 页面清单

| 页面 | 建议路由 | 主要用途 | 阶段 |
|---|---|---|---|
| 我的资源库 | `/library` | 私人资源、搜索、筛选、批量管理 | P0 |
| 新增资源 | `/new?type=color` | 统一新增入口，切换不同编辑器 | P0 |
| 资源详情 | `/resources/[id]` | 展示、复制、编辑入口、关联信息 | P0 |
| 编辑资源 | `/resources/[id]/edit` | 修改内容、分类、标签和发布状态 | P0 |
| 分类管理 | `/manage/categories` | 新增、重命名、移动、删除分类 | P0 |
| 标签管理 | `/manage/tags` | 合并重名标签、批量整理 | P0 |
| 合集 | `/collections/[id]` | 项目式收藏与手动排序 | P0 |
| 公开资源页 | `/explore` | 浏览主动公开的内容 | P0 |
| 公开分类页 | `/explore/categories/[slug]` | 按分类发布、浏览和分享 | P0 |
| 导入/导出 | `/settings/data` | 备份、恢复、旧资料迁移 | P0 |
| 偏好设置 | `/settings/preferences` | 默认复制格式、大小写、主题 | P0 |
| 工具工作台 | `/tools/*` | 对比度、转换、提色、渐变等 | P0 基础 / P1 增强 |
| 链接分享页 | `/s/[token]` | 仅持链接可访问的资源 | P1 |

### 4.2 资源库布局

桌面版采用“左侧导航 + 顶部搜索/新增 + 筛选区 + 主内容网格”。首屏直接展示内容，不做占满屏幕的宣传封面。

- 左侧：全部、单色、色板、网站、我的收藏、分类、合集、回收站。
- 顶部：全局搜索、当前复制格式、快速新增、账号菜单。
- 筛选：类型、分类、标签、公开/私有、排序；已选条件可逐个清除。
- 主区：规则网格卡片，提供舒适/紧凑两种密度；首版不做复杂瀑布流。
- 手机：侧栏改抽屉；筛选改面板；新增和复制操作不能依赖鼠标悬停。

### 4.3 视觉原则

以中性背景、清晰文字、少量界面强调色为主，让被收藏的颜色成为主角。浅色/深色界面都不得改变资源本身的色值。

页面换主题只改变“外壳”；“将当前色板应用到示例页面”必须发生在独立预览区，不能把整站导航和按钮一起染色。

使用统一间距、圆角、边框和等宽色值字体。加载、空状态、错误、无权限、保存冲突都需有独立反馈。空列表给出可直接点击的输入示例，不展示假收藏或虚假使用数据。

### 4.4 输入流程

1. 打开新增面板，直接聚焦输入框。
2. 输入合法颜色后立即显示预览；未完成输入显示“继续输入”，而非立即报错。
3. 输入单色时，默认标题为规范化色值，可选填中文名。
4. 检测到多个颜色时，让用户选择“保存为一个色板”或“分别保存为多个单色”。
5. 分类、标签可选填；可直接保存，不强迫完成复杂表单。
6. 首次保存进入私有草稿；公开发布是独立、明确的动作。

## 05. 多格式输入规范与颜色引擎

这是最需要先明确、先测试的模块。不要把解析逻辑零散写在页面组件里。

### 5.1 P0 支持的输入

| 格式 | 输入示例 | 处理规则 |
|---|---|---|
| 六位 HEX | `#FF0000`、`ff0000` | 输出默认带 `#`，支持大小写 |
| 三位 HEX | `#F00`、`f00` | 标准化为 `#FF0000` |
| 含透明度 HEX | `#F008`、`#FF000080` | 遵循 CSS 的 RGBA 顺序，透明度在最后 |
| RGB | `rgb(255, 0, 0)` | 支持传统逗号语法 |
| 现代 RGB | `rgb(255 0 0)`、`rgb(100% 0% 0%)` | 支持空格与百分比形式 |
| RGBA / alpha | `rgba(255,0,0,0.5)`、`rgb(255 0 0 / 50%)` | 保留透明度 |
| HSL / HSLA | `hsl(0,100%,50%)`、`hsl(0 100% 50% / 0.5)` | CSS 语法优先，不把 HSL 和 HSV 混用 |
| HSV / HSB | `hsv(0,100%,100%)`、`hsb(0,100%,100%)` | 本站扩展格式，明确标识“非 CSS 原生颜色函数” |
| CSS 英文色名 | `red`、`rebeccapurple`、`transparent` | 使用标准色名表，不猜任意名称 |
| RGB 数字三元组 | `255, 0, 0` | 明确按 0–255 RGB 解释，并显示识别结果 |

裸 HEX 先检查标准色名，再匹配 3/4/6/8 位十六进制字符。对于像 `bad` 这样的输入，需提示“按 HEX 识别为 #BBAADD”，避免用户误以为是色名。

裸三元组出现 `0.2, 0.4, 0.6` 等可能采用 0–1 量纲的输入时，要求用户选择“RGB 0–1 / RGB 0–255”，不隐式猜测。`1,0,0` 默认仍是明确写在界面上的 0–255 规则；0–1 模式需用户主动选择。

### 5.2 P1/P2 扩展输入

| 输入 | 阶段 | 必须满足的约束 |
|---|---|---|
| `hwb()` | P1 | 规范解析，保留原格式 |
| `lab()`、`lch()` | P1 | 正确处理参考白点与转换，不能直接当 RGB |
| `oklab()`、`oklch()` | P1 | 保留精度；超出 sRGB 时标注映射预览 |
| `color(display-p3 ...)` | P1 | 保留 P3 原值，提供明确标记的 sRGB 后备显示 |
| CSS 变量与样式块 | P1 | 用语法解析器提取；限定同一导入文档中的变量解析 |
| JSON / CSV 批量数据 | P0 | 按本站导入契约进行校验；不是执行代码 |
| 支持名单内的色板 URL | P1 | 优先解析 URL 内明确编码的色值，不承诺任意网站一键导入 |
| CMYK | P2 | 先收录原始参数；无配置文件时只允许注明条件的近似预览 |
| 专色/Pantone 等编号 | P2 | 作为名称和来源信息保存，不承诺无授权精确查表 |

CSS 颜色函数和 HEX 规则依据 [CSS Color Module Level 4](https://www.w3.org/TR/css-color-4/)；实现采用 [Culori API](https://culorijs.org/api/) 与其[颜色空间定义](https://culorijs.org/color-spaces/)，不自行重写整套色彩科学算法。

### 5.3 明确不自动求值的输入

`currentColor`、`var(--brand)`、`inherit`、`unset`、`light-dark()`、相对颜色以及需要上下文的 `color-mix()`，不能直接当成独立颜色保存。

首版显示“此输入依赖上下文，请提供具体颜色值”。后续 CSS 导入器只能在有完整、受限的变量上下文时解析；循环引用、外部样式依赖和无法求值的表达式必须报告，不返回假色值。

### 5.4 解析流水线

```text
保留原始文本
→ 长度/控制字符检查
→ 对适用场景做全角标点等输入辅助
→ 判断单色 / 数字三元组 / 多色 / 结构化导入
→ 使用格式适配器解析
→ 产生成功、未完成、无效、待消歧四类结果
→ 生成规范数据和显示格式
→ 色块预览
→ 服务端保存前再次校验
```

标准 CSS 中可合法归一化或截断的值，与真正的语法错误分开处理。例如超范围通道不能一概宣称“CSS 不合法”；按规范归一化后显示警告和实际值。自定义 HSV、裸三元组等扩展输入采用明确的范围校验。

**不要用 `split(',')` 直接拆多色输入。** `rgb()`、`hsl()` 和渐变中本来就有逗号。优先整段解析为单色；批量模式使用能识别括号层级和引号的分词器，只在顶层按换行、分号或合法分隔符拆分。

批量输入默认最多 200 个候选项。每项保留原文、识别结果和错误原因；允许“只导入已勾选的合法项”，但提交前必须明确显示被跳过数量。

### 5.5 核心数据原则

**原始输入是溯源记录，标准化坐标是计算基础，HEX 是一种显示/导出格式；三者不能混为一谈。**

建议每个颜色保存：

| 字段 | 作用 |
|---|---|
| `original_input` | 用户输入原文，便于原样复制与追溯 |
| `source_space`、`source_channels` | 可再现的源颜色空间与高精度通道 |
| `alpha` | 独立透明度，不隐藏在六位 HEX 中 |
| `xyz_d65` | 统一参考坐标，用于转换与比对；保留双精度 |
| `oklab`、`oklch` | 计算缓存，用于排序、近似搜索和建议色系 |
| `srgb_preview`、`hex_preview` | 显式标记的派生预览，不作为原始真值 |
| `in_srgb_gamut` | 是否能在 sRGB 色域内表示 |
| `parser_version`、`mapping_version` | 支持未来重新计算和回归测试 |

源坐标和原文保留，派生字段可以重建。数据库不能只保存一个 `hex` 字符串，也不能在保存时先将所有通道量化成 8 位。

### 5.6 显示、精度和透明度

- 普通、不透明的 8 位 sRGB 颜色：默认显示并复制六位 HEX。
- 带透明度的颜色：自动格式默认使用带 alpha 的 RGB 表达式；可手动切换 HEX8。
- HEX8 的 alpha 为 8 位量化值。例如 `0.5` 转为 `80` 后相当于 `128/255`，不能称为完全无损；原始 alpha 必须保留。
- 高精度或广色域颜色：默认优先显示源 CSS 表达式；切换 HEX 时注明“近似 sRGB”。
- 透明色使用棋盘格；支持切换白色、黑色和自定义底色预览。
- 色域映射算法必须固定并版本化；不得把超色域通道简单截断后声称“精确转换”。
- 计算使用高精度值，只在显示/导出层做明确的舍入；“复制原始输入”永远保持原文。
- CSS `#RRGGBBAA` 与其他工具的 ARGB 不自动混用。需要 ARGB 时提供显式转换入口。

## 06. 色块展示与一键复制

### 6.1 单色卡片规范

卡片包含大色块、规范色值、可选名称、分类/标签、收藏按钮和更多菜单。色值放在固定信息区，保证任何背景上均清晰可读。

**交互分工必须固定：点色块复制；点标题或详情按钮打开详情；点菜单管理；点复选框批量选择。** 不允许同一次点击既复制又跳转。

色块是独立按钮，不把菜单、链接或其他按钮嵌套在该按钮内部。白色和透明颜色也应有边界轮廓，不能在白底界面上“消失”。

### 6.2 复制格式

全局设置支持 `Auto / HEX / RGB / HSL / 原始输入`；P1 再增加 OKLCH 等格式。卡片可临时覆盖全局格式，并同步改变显示值。

- 显示 `#287F83`，点击就复制 `#287F83`，而不是复制另一种格式。
- 菜单提供“复制 HEX”“复制 RGB”“复制 CSS 声明”“复制原始输入”。
- 大小写、是否带 `#` 是显式偏好；只在 HEX 模式有效。
- 色板中的某个色块复制该颜色；“复制整个色板”是单独按钮。
- 复制结果允许与色值不同的情况，必须事先用动作名说明，例如“复制 CSS 变量”。

### 6.3 剪贴板与降级

主实现采用用户点击事件中的 `navigator.clipboard.writeText()`。只有 Promise 成功后才出现“已复制 #287F83”，并通过 `aria-live` 通知辅助技术。

权限拒绝、API 不可用或运行环境不支持时，弹出已选中的只读文本和手动复制提示；不显示虚假的成功状态，不要求读取用户剪贴板。

部署必须使用 HTTPS；开发时在受信任的本地环境测试。不要在写入剪贴板之前等待网络请求或完成与复制无关的异步任务。相关限制见 [MDN Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API) 和 [writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText)。

### 6.4 必须覆盖的交互环境

桌面鼠标、触屏、键盘 Enter/Space、权限被拒绝、浏览器隐私模式、Mac Safari、iPhone Safari，以及 Firefox/Chromium。

自动化 WebKit 测试不能替代真实 Safari 的剪贴板验收。批量选择模式启用时，应明确改变点击行为并显示模式提示，不让复制与选择互相抢事件。

## 07. 色板收藏与编辑

首版支持 2–24 个颜色组成一个色板，推荐日常使用 3–8 色；数量上限做成配置，不写死在组件中。

### 7.1 编辑能力

添加、删除、替换、拖动排序；同时提供键盘可操作的“前移/后移”。支持从已有单色选择，也支持直接输入一组颜色。

每个颜色可设置角色：`background`、`text`、`primary`、`secondary`、`accent`、`border`、`muted` 或自定义角色。角色允许为空；一般色板不强迫套用网页主题结构。

保存名称、用途、分类、标签、说明、来源；允许复制现有色板生成新版本。P1 再增加锁定部分颜色、按规则补全、反转顺序、编辑历史。

### 7.2 重要语义

“把单色加入色板”默认复制一个颜色快照。以后修改单色，不自动改变所有已引用的色板。需要追踪来源时保存来源资源 ID，但不默认为实时绑定。

色板可以包含重复颜色，因为角色可能不同。去重只能是提示或用户主动操作，不得自动删除。

### 7.3 导出

P0 支持纯文本、JSON、CSS 变量。P1 增加 PNG/SVG 色板图、SCSS、符合目标规范的设计令牌导出和图表颜色数组。

CSS 变量名必须可预测、合法、唯一；根据角色生成，例如 `--color-primary`。自定义名称要进行转义与去重，不把用户任意字符串直接拼成代码。

## 08. 颜色网站与知识资源收藏

### 8.1 网站书签字段

| 字段 | 必填 | 说明 |
|---|---|---|
| URL | 是 | 原始地址与规范化地址分别保存 |
| 名称 | 是 | 默认可用域名，之后允许修改 |
| 简介 | 否 | 用户自己的用途说明 |
| 分类、标签 | 否 | 如配色生成、取色、可访问性、图表 |
| 使用场景 | 否 | PPT、UI、印刷参考、科研、学习 |
| 语言、费用标签 | 否 | 免费/付费等是人工记录，附核查日期，不保证永久有效 |
| 个人评分/私有备注 | 否 | 与公开简介分开保存，默认不公开 |
| 来源和核查时间 | 否 | 记录何时加入、何时确认可访问 |
| 图标/缩略图 | 否 | 首版以站点首字母图标降级，不依赖远程图标 |

### 8.2 首版：手动保存必须可靠

输入 URL 后，只要地址格式合法，即可手动填标题并保存。网站阻止抓取、登录可见、超时或没有 Open Graph 信息，都不应导致收藏失败。

点击“访问网站”新标签页打开，外链使用安全的 opener/referrer 策略。资源卡片保留清晰域名，让用户知道将访问哪个网站。

### 8.3 第二阶段：可选的元数据获取

用户主动点击“获取标题/简介”后，由服务器受控抓取标题、描述、站点名和可选图标。抓取结果是建议值，不覆盖已编辑内容。

不默认内嵌第三方网站，不假设对方允许 iframe；不抓取付费内容，不绕过登录或反自动化限制。网站健康检查也必须遵守相同安全限制。

### 8.4 URL 去重规则

标准化协议和主机大小写，去除已知跟踪参数；保留可能决定页面内容的参数、路径大小写和有效锚点。不能简单删掉全部查询参数。

相同规范化 URL 在当前用户的资源库中提示重复；允许“打开已有”“合并标签”“仍然另存”。不跨用户披露谁收藏过相同网址。

### 8.5 文章与图片关联

P1 可以将教程链接、自写笔记、图片灵感关联到单色或色板。站内文章优先保存自写内容或摘要加来源，不把整篇第三方文章默认复制到自己的站点。

## 09. 分类发布、权限与收藏管理

### 9.1 状态与可见性分离

`status = draft | published | archived`；`visibility = private | public | unlisted`，其中 `unlisted` 在 P1 启用。

对普通访客可公开读取的必要条件为：

```text
status = published
AND visibility = public
AND deleted_at IS NULL
```

私有草稿可以编辑、收藏和导出，但不能出现在公开列表、搜索建议、分类数量、站点地图或分享图片里。

### 9.2 发布流程

保存草稿 → 预览公开视图 → 确认标题、分类、来源和公开字段 → 发布。

公开预览中不显示私有笔记和内部评分。撤回发布后，公开页面、搜索和缓存应同步失效。复制的外部文件无法远程撤回，这一点在分享说明中明确。

公开内容编辑时，首版采用“明确点击保存并更新公开内容”的规则；取消或离开编辑页不影响线上版本。完整的独立修订草稿与版本发布系统放 P2。

### 9.3 首版角色

| 能力 | 访客 | 站长 |
|---|---|---|
| 浏览公开资源与复制色值 | 可以 | 可以 |
| 浏览私有资源 | 不可以 | 仅本人 |
| 新增、编辑、删除、分类 | 不可以 | 本人资源 |
| 发布、撤回和导出私有数据 | 不可以 | 本人资源 |
| 管理站点与账号 | 不可以 | 可以 |

默认关闭开放注册，避免把单用户工具直接变成需要反垃圾和审核的社区。未来增加用户后必须继续验证跨用户隔离。

### 9.4 合集与隐私

合集可以跨类型收录资源并自定义排序。公开合集只能展示其中已公开发布的资源；把私有颜色放进公开合集不会自动公开它。

发布前列出不符合公开条件的成员并提示处理；访客界面不得透露隐藏成员的标题、数量或缩略图。公开合集导出同样按可见性过滤。

### 9.5 仅链接访问（P1）

使用高强度随机分享令牌，支持撤销和可选到期时间。服务端验证令牌后只返回允许字段；数据库中保存令牌哈希。

**不能为了实现 unlisted，就把所有 unlisted 记录开放给匿名数据库查询。** 令牌授权只能走独立服务端入口；公开查询仍然只读 public。链接可被持有人转发，因此不等于机密访问控制。

### 9.6 管理操作

支持批量分类、标签、收藏、归档、软删除与恢复。删除分类时要求选择“移入未分类”或“重新归类”，默认不删除其中资源。

回收站默认保留 30 天，可配置；物理清理任务未实现前不向用户承诺自动清理。重要删除与发布操作记录审计事件。

## 10. 搜索、筛选、去重与推荐

### 10.1 首版搜索

支持标题、中文名、英文名、标签、公开简介、网站域名和色值。输入颜色值时，先尝试解析为颜色，再提供“查找此颜色”的专门结果；普通文本仍按文本检索。

精确颜色检索不能只比较输入字符串。例如 `red`、`#FF0000` 和 `rgb(255 0 0)` 应能找到相同的颜色候选。

结果可按更新时间、创建时间、名称和手动合集顺序排序。先做稳定分页，每页默认 48 项；数据量增大后采用键集游标，不一次下载整个资源库。

### 10.2 中文检索策略

首版采用 PostgreSQL 的规范化字段检索、受控 `ILIKE` 与可用的 `pg_trgm` 索引。中文二字关键词、单字标签及中英混输必须独立测试，不能只因为建了全文索引就宣称“支持中文搜索”。

`pg_trgm` 的索引与相似文本查询能力见 [PostgreSQL 官方文档](https://www.postgresql.org/docs/current/pgtrgm.html)。对无法有效使用索引的短查询，限制候选规模和结果数；实际出现搜索瓶颈后再引入专用搜索引擎。

### 10.3 去重原则

相同颜色值可以有不同名称、来源和项目用途，因此只提示重复，不建立禁止重复收藏的全局唯一约束。

对于普通 8 位 sRGB，使用完整颜色和 alpha 生成精确匹配键；对于高精度与广色域输入，用源数据及标准坐标辅助比对，不能依据映射后的 HEX 自动合并。网站重复规则见第 08 节。

导入时提供跳过、另存和明确选择的合并操作。任何会丢失来源、角色或备注的自动合并都禁止。

### 10.4 P1 相近颜色搜索

保存 OKLab/OKLCH 派生坐标，先筛选候选，再按固定的感知色差方法排序。明确使用哪个距离和量纲，不混用不同 ΔE 指标的阈值。

初版只比较已授权可见资源；透明度不同的颜色不能当成相同视觉效果。可提供“按原颜色比较”与“叠加到指定背景后比较”两种模式。

色系、冷暖、深浅、低饱和等标签都是可调整的产品规则，不是绝对事实。无彩色需单独处理，不能让无意义的 hue 决定分类。用户可以覆盖自动建议。

## 11. 工具工作台与扩展边界

| 工具 | 主要交互 | 阶段 | 边界 |
|---|---|---|---|
| 颜色转换 | 输入一个颜色，查看多种格式 | P0 | 与收藏编辑器共用引擎 |
| 基础对比度 | 指定文字色和背景色，显示结果 | P0 | 只评价当前组合和条件 |
| 图片取色 | 上传/粘贴图片、选取位置、提取候选色 | P1 | 默认本地处理，不擅自上传图片 |
| 屏幕取色 | 浏览器支持时启用吸管 | P1 | 不作为唯一取色方式 |
| 渐变编辑 | 颜色、位置、角度和预览 | P1 | 首先只做线性渐变 |
| 规则配色 | 输入主色、选择和谐规则、锁定颜色 | P1 | 规则输出不保证“审美最优” |
| 色阶生成 | 从主色生成一组深浅色 | P1 | 不声称某一色阶天然适合所有按钮状态 |
| 场景预览 | 网页/PPT/图表模板中切换色板 | P1 | 不改变站点外壳 |
| 色觉模拟 | 选择模拟类型、对比原图 | P1 | 模拟不是可访问性认证 |
| 设计令牌 | 定义语义角色和主题，导出 | P2 | 使用有版本的格式适配器 |
| AI 推荐 | 描述场景、产生候选、验证后收藏 | P2 | 生成结果必须经同一引擎校验 |

### 11.1 图片取色

图片上传与颜色提取分开：用户可以只在本地取色而不保存原图。优先支持 PNG、JPEG、WebP；首版图片模块不接受可执行 SVG 或任意文档。

提供“点选取色”和“提取 3–12 个候选色”。自动提色不是唯一正确答案，用户可改数量、删除背景色并手工调整。透明像素需过滤或明确选择合成背景。

需记录提取算法、图像解码/色彩空间假设和版本；不宣称任意 ICC 图片都能在不同设备上得到完全一致的结果。外链图片可能无法直接读取，提供本地上传，不绕过访问限制。

[EyeDropper API](https://developer.mozilla.org/en-US/docs/Web/API/EyeDropper_API) 兼容性有限，必须做能力检测；不支持时保留输入、上传图片和图片内取色。

### 11.2 渐变

P1 第一版只支持单层 `linear-gradient`：2–24 个色标、角度、百分比位置、透明度和明确的插值策略。径向、锥形、重复渐变放后续版本。

渐变保存结构化参数，而不是只保存 CSS 字符串。复制按钮明确是“复制 CSS 渐变”，不能伪装为单个色值。色标位置相同可能用于硬切边，不应被自动去重。

对复杂的导入渐变，无法支持的语法要提示，不做不透明的近似重建。导出时固定插值策略，并提示不同输出目标可能有渲染差异。

### 11.3 场景预览

网页模板含标题、正文、卡片、按钮和表单；PPT 模板含封面、内容页、图表页；图表模板含柱状图、折线图和热力图。

需要用户指定或确认颜色角色，不能把任意顺序的 5 个颜色自动认定为背景、文字、主色等。示例页面使用隔离的 CSS 变量作用域。

PPT 预览是网页中的模拟样张，不等于导出 PPTX。真实 PPTX、专业印刷文件等输出作为独立后续需求估算和验收。

### 11.4 对比度与可访问性

按 [WCAG 2.2 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)：普通文字 AA 为至少 4.5:1，大号文字 AA 为至少 3:1；大号文字按规范的字号/字重条件判断，不只凭视觉大小。

透明颜色必须先与用户指定的底色合成，再计算实际前景/背景组合。对比度使用明确的 sRGB 计算路径；广色域内容若使用 sRGB 映射预览，需在结果上标明这一条件。

不要给整套色板一个不加条件的“无障碍通过”标签。应显示“哪一个前景、哪一个背景、哪个字号条件、采用何种映射”通过或未通过。

重要控件与信息图形的非文本对比要求另行测试，见 [W3C 非文本对比度](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html)。不能只用红/绿表示状态，需同时提供文字或符号。

## 12. 推荐技术方案

### 12.1 主方案

| 层 | 选型 | 在本项目中的职责 |
|---|---|---|
| Web 框架 | [Next.js](https://nextjs.org/docs) + React + TypeScript | 公开页面渲染、私有工作台、API 路由 |
| 样式 | [Tailwind CSS](https://tailwindcss.com/docs/theme) + CSS 自定义属性 | 布局、界面主题、隔离的预览主题 |
| 基础组件 | [shadcn/ui](https://ui.shadcn.com/docs) | 对话框、下拉菜单、表单、提示等；色块组件自行实现 |
| 颜色引擎 | [Culori](https://culorijs.org/) | 解析、转换、色差与色域相关计算 |
| 运行时校验 | [Zod](https://zod.dev/) | 输入、API、数据库写入与导入文件校验 |
| 后端服务 | [Supabase](https://supabase.com/docs/guides/getting-started/quickstarts/nextjs) | PostgreSQL、认证、后续文件存储 |
| 权限 | PostgreSQL RLS + 服务端授权 | 资源归属、公开内容与私有内容隔离 |
| 单元/组件测试 | [Vitest](https://vitest.dev/guide/) | 颜色引擎、格式化、解析与业务规则 |
| 端到端测试 | [Playwright](https://playwright.dev/docs/intro) | 浏览器流程、权限、导入/导出和兼容性 |

选择依据是统一 TypeScript 栈和减少首版基础设施，而不是这些组件“唯一正确”。依赖使用实施时互相兼容的稳定版本、记录选择理由并提交 lockfile；不在本计划里固定未经联调的版本组合。

### 12.2 架构边界

```text
浏览器
  输入、即时预览、格式切换、复制、排序、临时草稿
  │
  ├─ 共享 color-core：纯函数，不访问网络和数据库
  │
  └─ 同源 API / 服务端页面
       认证身份 → 参数校验 → 业务服务 → 数据库事务
       │                                  │
       │                                  └─ PostgreSQL + RLS
       └─ P1 受控任务：元数据抓取 / 附件处理 / 分享链接
```

颜色输入和复制必须能在短暂断网时继续使用；服务器不可用时，新内容只标为本地草稿，不能显示“已同步”。首版不实现离线双向同步、冲突自动合并或复杂 PWA。

服务端渲染页面只返回需要的字段。交互重的编辑器使用客户端组件，静态展示不必把完整颜色库和所有工具模块装入首屏。

### 12.3 数据访问方式

首版统一由同源 API 调用业务服务进行写入，避免同一操作同时存在前端直写数据库、Server Action 和 REST 三套实现。

用户操作使用带用户身份的数据库客户端，让 RLS 生效；浏览器不得拿到 service-role 或其他高权限密钥。SSR 会话接入遵循 [Supabase 服务端认证文档](https://supabase.com/docs/guides/auth/server-side)。

公开页面与私有页面使用不同的数据读取契约和缓存策略；私有响应禁止进入公共 CDN 缓存。服务端接口不能只依靠“按钮在前端隐藏了”实现权限。

### 12.4 暂不引入的复杂度

首版不需要微服务、Kubernetes、向量数据库、实时协作、消息总线或独立搜索集群。只有量化瓶颈或明确需求出现时再增加组件。

图片提色等计算先在浏览器处理；远程元数据抓取 P1 才增加受限任务执行器。队列/Worker 的引入不应成为 P0 颜色收藏的前置条件。

### 12.5 部署选择

默认采用托管 Next.js 运行环境与 Supabase；服务商、区域、额度和价格在实际部署时核查，不把当前免费额度当成永久承诺。

需要自托管时，可运行 Node/Docker 版本的应用并使用兼容 PostgreSQL、认证和对象存储方案。自托管 Supabase 是独立运维选择，不等同于“只换一个数据库地址”即可完成。

面向不同访问地区时，实测应用、认证、数据库、附件和邮件链路；不把关键界面建立在必须实时访问第三方字体、图标或外部网站的前提上。

## 13. 共享颜色模型与模块契约

以下 TypeScript 是建议的数据契约轮廓，实施时用 Zod 补全各颜色空间的通道、范围和有限数校验。

```ts
type ParseState = 'valid' | 'incomplete' | 'invalid' | 'ambiguous';
type CopyFormat = 'auto' | 'hex' | 'rgb' | 'hsl' | 'oklch' | 'original';

type ColorSpace =
  | 'srgb' | 'hsl' | 'hsv' | 'hwb'
  | 'lab' | 'lch' | 'oklab' | 'oklch' | 'display-p3';

interface ColorValue {
  schemaVersion: 1;
  originalInput: string;
  source: {
    space: ColorSpace;
    channels: [number, number, number];
  };
  alpha: number;
  xyzD65: [number, number, number];
  preview: {
    css: string;
    hex: string;
    inSrgbGamut: boolean;
    approximate: boolean;
  };
  engineVersion: string;
  mappingVersion: string;
}

interface ParseIssue {
  code: string;
  message: string;
  start?: number;
  end?: number;
}

type ParseResult =
  | { state: 'valid'; value: ColorValue; warnings: ParseIssue[] }
  | { state: Exclude<ParseState, 'valid'>; issues: ParseIssue[] };

interface CopyPayload {
  text: string;
  format: CopyFormat;
  approximate: boolean;
  warnings: string[];
}
```

P0 不接受无法求解的缺失通道；如果 P1 支持 CSS `none` 等语义，需要先升级 schema，而不是往数字字段塞 `NaN`。灰色的派生 hue 可以在缓存层为空，但必须有明确序列化规则。

### 模块职责

| 模块 | 责任 | 不应承担的责任 |
|---|---|---|
| `parseColorInput` | 单色识别、规范化、错误分类 | 保存数据库、弹 Toast |
| `parseColorBatch` | 分词、逐项解析、返回位置与错误 | 自动丢弃失败条目 |
| `formatColor` | 根据复制/显示格式生成输出 | 擅自修改原始值 |
| `getPreviewColor` | 生成目标色域预览及映射标记 | 将预览覆盖成源颜色 |
| `getContrast` | 在明确背景与计算条件下计算 | 声称整个设计完全无障碍 |
| `compareColors` | 返回指定指标的距离 | 决定是否自动合并资源 |
| `copyText` | 写剪贴板、返回成功或失败 | 读取剪贴板、记录私人颜色值 |
| `resourceService` | 权限、业务规则、事务 | 包含 UI 或浏览器 API |
| `importService` | 文件验证、预览、映射、幂等导入 | 执行导入的 JS/HTML/CSS |

前后端引入同一 `color-core`，但服务端必须重新解析输入，不能相信客户端提交的“已经归一化”数值。

## 14. 数据库设计

### 14.1 主要数据表

| 表 | 核心字段 | 说明 |
|---|---|---|
| `profiles` | `id`, `display_name`, `preferences` | 关联认证用户；站长权限不放在用户可随意修改的字段里 |
| `resources` | `id`, `owner_id`, `type`, `title`, `aliases`, `description`, `source_url`, `source_kind`, `source_metadata`, `status`, `visibility`, `version`, 时间戳 | 所有资源共用的管理与权限入口；aliases 支持英文名，source_metadata 记录 legacy ID 和场景信息 |
| `resource_colors` | `id`, `resource_id`, `position`, `role`, `label`, 源坐标、alpha、标准坐标、派生预览、引擎版本 | 单色、色板、渐变、图片关联色共用 |
| `website_details` | `resource_id`, `original_url`, `normalized_url`, `site_name`, `metadata`, `checked_at` | 网站专属字段 |
| `gradient_details` | `resource_id`, `kind`, `angle`, `interpolation`, `stops` | P1；色标引用同资源的颜色条目 |
| `image_details` | `resource_id`, `asset_id`, `source_credit`, `extraction_settings` | P1；图片来源、提色方法与设置 |
| `article_details` | `resource_id`, `body_markdown`, `external_url` | P1；正文默认不支持原始 HTML |
| `categories` | `id`, `owner_id`, `parent_id`, `name`, `slug`, `sort_order` | 自定义分类树 |
| `resource_categories` | `resource_id`, `category_id`, `is_primary` | 多分类关联 |
| `tags` | `id`, `owner_id`, `name`, `normalized_name` | 用户范围内规范化去重 |
| `resource_tags` | `resource_id`, `tag_id` | 多对多关联 |
| `collections` | `id`, `owner_id`, `name`, `description`, `visibility` | 跨类型项目合集 |
| `collection_items` | `collection_id`, `resource_id`, `position` | 收藏顺序与成员关系 |
| `user_resource_state` | `user_id`, `resource_id`, `is_favorite`, `pinned_at` | 私人的收藏/置顶状态，不能改写成全站属性 |
| `resource_private_notes` | `resource_id`, `owner_id`, `body`, `rating` | 与公开记录分表，避免公开接口误带私有信息 |
| `assets` | `id`, `owner_id`, `storage_path`, `mime`, `size`, `hash` | P1；文件记录，不存公开永久链接作为唯一标识 |
| `share_links` | `id`, `resource_id`, `token_hash`, `expires_at`, `revoked_at` | P1；仅通过专用服务端验证 |
| `import_jobs` | `id`, `owner_id`, `source_hash`, `idempotency_key`, `result` | 导入幂等、映射与失败报告 |
| `audit_events` | `id`, `actor_id`, `resource_id`, `action`, `created_at` | 记录发布/删除/恢复等，不记录剪贴板内容 |

P0 只创建实际需要的表；P1 的表在对应迁移中增加。统一 `resources` 并不意味着把所有内容塞进一个无约束 JSON 字段。

### 14.2 约束与事务

- UUID 为资源标识；时间采用带时区时间戳并按 UTC 存储，界面按用户时区显示。
- 每个颜色通道必须为有限数；alpha 限制在 `[0,1]`；源颜色空间决定其他通道校验规则。
- `color` 资源恰有一个颜色；`palette` 有 2–24 个；发布/保存时由事务内校验与数据库约束/触发器共同保证。
- 主分类至多一个；分类树禁止循环、跨用户父节点和超过上限的层级。
- 同一资源内颜色顺序唯一；重排在事务中执行，避免交换位置时产生临时冲突。
- 标签、分类、合集与资源的关联必须验证所有权，不能把自己的资源偷偷关联到其他用户的私有集合。
- `version` 用于乐观并发控制；两个标签页同时编辑时，后提交者收到冲突提示，而不是默默覆盖。
- 软删除记录使用 `deleted_at`，恢复前检查关联数据仍然可用。

### 14.3 索引

先为真实查询建立以下索引，再用执行计划验证：

| 查询 | 建议索引 |
|---|---|
| 我的资源按更新时间分页 | `resources(owner_id, updated_at DESC, id)`，未删除部分索引 |
| 公开资源按类型和发布时间查询 | 已公开发布且未删除的部分索引，包含 `type, published_at, id` |
| 分类/标签过滤 | 关联表的两个方向均有合适的复合索引 |
| 颜色顺序读取 | `resource_colors(resource_id, position)` |
| 精确色值候选查找 | 规范化匹配键索引；查询结果仍经资源权限过滤 |
| URL 重复提示 | 规范化 URL 的查找索引；查询限定所有者 |
| 关键词搜索 | 按实测选择规范化文本字段和 trigram 索引 |

避免列表逐项读取颜色、标签、分类而造成 N+1 请求。首版不做大规模向量检索，也不为尚不存在的查询建立大量索引。

### 14.4 RLS 与公开字段

所有用户数据表、关联表和附件元数据都启用最小权限策略。主资源私有时，不能通过直接查颜色子表、标签关联、附件记录或导出接口绕过权限。

公开读取只匹配 published + public + 未删除；所有者可读取自己的草稿和私有内容。 访客只读取已公开资源所需的分类/标签展示字段和经授权的祖先路径，不返回私人分类树及私有数量。写入使用 `WITH CHECK` 等规则校验新记录归属；多表关联同时核验两个端点。

`resource_private_notes` 仅所有者可读，不与公开数据直接 `select *` 联合输出。对公开字段使用显式 DTO 白名单。原理与实现边界见 [Supabase RLS 文档](https://supabase.com/docs/guides/database/postgres/row-level-security)。

## 15. API 设计与错误契约

### 15.1 首版接口

| 方法与路径 | 作用 | 关键要求 |
|---|---|---|
| `GET /api/resources` | 我的资源分页与筛选 | 必须认证、服务端限制 owner |
| `GET /api/public/resources` | 公开资源分页 | 只返回公开 DTO，无私有计数 |
| `POST /api/resources` | 创建资源 | 服务端解析颜色，事务写入 |
| `GET /api/resources/:id` | 授权后的详情 | 不可访问与不存在保持一致的外部响应策略 |
| `PATCH /api/resources/:id` | 编辑资源 | 必须携带 `expectedVersion` |
| `POST /api/resources/:id/publish` | 发布 | 校验完整性和公开字段 |
| `POST /api/resources/:id/unpublish` | 撤回 | 使公开缓存与索引失效 |
| `DELETE /api/resources/:id` | 软删除 | 可恢复；不级联删除外部来源资源 |
| `POST /api/resources/:id/restore` | 恢复 | 验证所有者与保留条件 |
| `POST /api/resources/batch` | 批量管理 | 限制数量，明确逐项结果或事务规则 |
| `GET/POST/PATCH/DELETE /api/categories` | 分类管理 | 防循环与跨用户关联 |
| `GET/POST/PATCH/DELETE /api/tags` | 标签管理 | 规范化与合并策略明确 |
| `GET/POST/PATCH/DELETE /api/collections` | 合集管理 | 可见性、成员授权和顺序 |
| `POST /api/imports/preview` | 验证导入数据 | 不写入最终资源 |
| `POST /api/imports/commit` | 确认导入 | 幂等，绑定预览内容哈希与用户 |
| `POST /api/exports` | 导出授权数据 | 私有导出不使用公共缓存 |

对分类/标签/合集的单项更新和删除使用 `/:id` 子路径；表中合并展示是接口族，不表示删除整个集合。

### 15.2 创建请求示例

```json
{
  "type": "color",
  "title": "教学青绿",
  "description": "用于课堂材料的主色候选。",
  "colors": [
    { "input": "#287F83", "position": 0, "role": "primary" }
  ],
  "categoryIds": [],
  "tagIds": [],
  "status": "draft",
  "visibility": "private"
}
```

服务器返回规范化资源与版本号。不得接受客户端自行指定 `owner_id`、审核权限或已经计算好的“可信颜色坐标”。

### 15.3 错误结构

```json
{
  "error": {
    "code": "INVALID_COLOR",
    "message": "第 2 个颜色无法解析。",
    "field": "colors[1].input",
    "details": { "input": "#12" }
  },
  "requestId": "generated-request-id"
}
```

错误码至少覆盖：`INVALID_COLOR`、`AMBIGUOUS_COLOR`、`UNSUPPORTED_FORMAT`、`FORBIDDEN`、`NOT_FOUND`、`VERSION_CONFLICT`、`IMPORT_LIMIT_EXCEEDED`、`DUPLICATE_CANDIDATE`。

输入错误 400/422、未认证 401、禁止访问 403 或不暴露存在性的 404、版本冲突 409、超限 413/429；服务端日志保留请求 ID，但避免记录私有笔记与完整导入内容。

### 15.4 P1 接口

`/api/bookmarks/metadata`、`/api/assets/*`、`/api/share-links/*` 等独立增加。不要为了这些后续接口先暴露不受限的通用 URL 代理或文件上传入口。

## 17. 导入、导出、备份与旧资料迁移

### 17.1 首版格式

| 格式 | 用途 | 精度与限制 |
|---|---|---|
| 本站 JSON | 完整迁移与备份 | 主要可恢复格式，含 schemaVersion 和高精度源数据 |
| CSV | 批量录入与表格编辑 | 扁平化格式；不宣称完整保留所有关系 |
| CSS 变量 | 在网页中复用色板 | 输出角色与值，不承担账户/分类备份 |
| 纯文本 | 快速复制和交换颜色 | 无元数据，不作为完整备份 |

JSON 包含资源、颜色、分类、标签、合集和来源；私有笔记只有所有者主动导出时才包含。不得导出登录会话、密钥或有效分享令牌。

### 17.2 JSON 外层契约

```json
{
  "schemaVersion": 1,
  "product": "color-atlas",
  "exportedAt": "2026-10-25T00:00:00Z",
  "resources": [],
  "categories": [],
  "tags": [],
  "collections": []
}
```

上面的时间仅是格式示例，实际导出由程序生成当前 UTC 时间。每个资源同时携带类型和该类型的验证结构。

导入遇到高于当前支持的 schemaVersion 时停止并提示，不丢弃未知字段后强行导入。未来升级提供显式版本迁移器。

### 17.3 CSV 约定

建议字段：`group_key,type,title,color_input,color_position,color_role,url,categories,tags,description,source_url`。

同一色板使用相同 `group_key`；每个颜色一行；分类/标签在单元格内采用明确约定的分隔符和标准 CSV 引号转义。不能依赖字符串 `split(',')` 读取 CSV。

提供下载模板和导入预览；对公式前缀等危险文本进行安全导出处理并记录约定，防止用户在表格软件中打开时执行意外公式。

### 17.4 导入流程与限制

上传 → 结构验证 → 映射字段 → 列出新增/重复/错误 → 用户确认 → 分批事务写入 → 导入报告。

建议首版导入上限为 5 MB、2,000 项资源；这是可配置保护值。超限明确提示，不让页面卡死。单资源创建原子化；大文件按批次处理，并准确报告已成功和失败项，不宣称整个任务天然全局原子。

导入 ID 重映射到当前用户，不接受文件声明的所有者和权限。默认导入为私有草稿；恢复发布状态需要单独确认。使用幂等键与来源哈希防止重复点击导致成倍导入。

### 17.5 迁移已有 Color Atlas 资料

已有文件：`color-atlas-palettes.html`、`color-atlas-quick-reference.md`。HTML 中包含 12 套配色与 15 个网站，并已有导出数据结构：

```text
{ title, palettes: [...], sites: [...] }
```

建议直接使用旧页面导出的 JSON，或在开发期用只读取静态数组的脚本迁移；禁止为了导入而执行任意上传 HTML 中的 JavaScript。

| 旧字段 | 新字段/处理 |
|---|---|
| `id` | 导入来源中的 legacy ID，非跨用户主键 |
| `name` / `en` | 标题 / 英文别名 |
| `desc` | 说明 |
| `category` | 可编辑分类映射 |
| `bg` | 角色 `background` 的颜色 |
| `ink` | 角色 `text` 的颜色 |
| `primary` | 角色 `primary` 的颜色 |
| `soft` | 角色 `muted` 的颜色 |
| `accent` | 角色 `accent` 的颜色 |
| `tag` | 标签 |
| `theme` | 场景预览示例文案 |
| `contrast` | 不直接视为可信测试结论，按当前引擎和指定配对重新计算 |
| 网站 `name,url,type,detail` | 网站标题、URL、分类/标签、简介 |

这些配色是前次整理的场景化建议，不标记为 Color Hunt、Adobe 或其他网站的官方方案。导入过程保留这一来源说明。

### 17.6 恢复验证

上线前完成一次“导出 → 空白测试库导入 → 比较数据”的演练，比较数量、颜色源值、alpha、顺序、分类关系、来源和私有备注。原始业务数据不完整恢复，就不能把功能命名为“完整备份恢复”。

P1 加入图片后，需单独提供附件清单、文件校验与打包恢复流程；只有 JSON 而没有图片文件不算完整附件备份。

## 18. 安全、可访问性与性能要求

### 18.1 输入与渲染安全

颜色输入必须整体解析成功；禁止只提取某个合法前缀后忽略剩余恶意内容。颜色预览只接受引擎输出的受控 CSS 值，不把任意输入插入 `style`、HTML 或脚本。

标题、标签、网址、简介、导入数据和远程元数据都视为不可信输入。Markdown 默认禁用原始 HTML，后续允许的内容经白名单净化；禁止 `eval` 和执行导入代码。

网站 URL 只允许明确支持的 HTTP/HTTPS 形式，拒绝 `javascript:`、`data:`、凭据嵌入式地址及控制字符。需要补全 `https://` 时，在保存前展示最终地址。

认证 Cookie 和写入接口配置 CSRF/Origin 防护；限制登录、创建、导入、导出和抓取频率。所有写入均做服务端校验，不能只依赖前端表单。

### 18.2 远程元数据抓取安全（P1）

这是服务器访问用户提供地址的高风险入口，实施前参考 [OWASP SSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

必须限制协议、端口、响应体大小、内容类型、超时和重定向次数；阻止环回、私网、链路本地、云元数据等不可访问地址，覆盖 IPv4/IPv6。

DNS 解析结果和每一次重定向目标都需校验，并在实际连接阶段保持限制，避免只在最初检查域名。配合受限出网策略，不把抓取器放在可访问内网管理接口的环境里。

首版抓取器只读必要文本元数据，不运行第三方 JavaScript，不携带站长 Cookie 或其他凭据。图标/缩略图请求也适用相同限制。任何安全检查失败都退回手动录入。

### 18.3 文件与隐私（P1）

上传检查扩展名、文件签名、实际解码结果、像素数量和大小；随机生成存储名称。图片移除不必要元数据，对可展示副本进行安全重编码。实践依据见 [OWASP 文件上传防护](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

私有附件和缩略图不得放进永久公开存储桶；通过授权读取或短时签名 URL 访问。撤回公开后立即拒绝新的应用访问；已经发出的签名链接以其短有效期为边界，已下载内容无法撤回。

本地图片提色默认不上传；使用远程 AI 服务分析私人内容前必须获得明确授权。日志不采集剪贴板、完整图片、私有笔记或访问令牌。

### 18.4 可访问性

全站支持键盘操作、可见焦点、明确按钮名称和屏幕阅读器。拖动排序提供替代按钮；错误提示和成功反馈不只靠颜色。

卡片色值使用高对比文字区。需要把文字叠在色块上时，基于实际合成底色选择可读文字，不用简单的 RGB 平均值判断明暗。

减少不必要动画，尊重减少动态效果偏好。移动端触控区域与菜单操作需人工测试，不把自动化扫描“零错误”当成全部无障碍通过。

### 18.5 建议性能目标

测试记录必须注明浏览器、硬件、网络、部署区域和数据规模。以下为验收目标，不是性能承诺。

| 场景 | 建议目标 |
|---|---|
| 单色输入解析与预览 | 指定测试设备上 P95 小于 50 ms |
| 复制动作 | 100 ms 内开始反馈；成功状态必须等待真实写入成功 |
| 批量解析 200 个颜色 | 指定桌面环境下小于 500 ms；超出时避免阻塞主线程 |
| 资源列表 | 1 万项资源、5 万条颜色记录下正常分页，不下载全部记录 |
| 搜索接口 | 同区域测试条件下 P95 小于 500 ms |
| 公开页首屏 | 以 LCP 2.5 秒以内为优化目标，记录实际测试条件 |
| 私有页缓存 | 不进入公共 CDN 缓存，不因账号切换展示另一用户结果 |

图片懒加载，预览图使用适当尺寸；工具按页面加载，颜色引擎按需导入。只有实际出现大量卡片渲染瓶颈时才增加虚拟列表。

### 19.2 数值测试

建立覆盖代表色、灰色、边界色、极低 alpha、色相跨 0/360 和格式变体的 fixture。P0 支持格式全部必须有正例和反例。

8 位 sRGB 的常规往返转换应恢复相同字节值；源 alpha 不因显示切换而变化。高精度转换按具体路径定义数值容差，并记录在测试里，而非只比较截图看起来是否一样。

固定一组官方规范示例和独立基准结果校验颜色核心。库升级时重新跑 fixture、对比度和色域映射回归；不得因升级悄悄改变已保存的源值。

### 19.3 首版发布门槛

P0 用例通过；没有已知的跨用户数据泄露、颜色静默错误、假保存成功或假复制成功。真实 Safari 验收、备份恢复、生产环境 HTTPS 和至少一次迁移演练完成。

未来格式、图片、AI 功能尚未实现时不在生产界面放“可点击但无功能”的入口；需要展示路线图时，明确标注尚未提供。

## 21. 部署、运维与交付清单

### 21.1 环境与发布

开发、测试、生产分开；测试账号与数据不得连接生产库。环境变量只在服务端或适当的公开配置边界使用，真实秘密不写入仓库和示例文件。

CI 至少执行：静态检查 → 类型检查 → 颜色引擎单测 → 数据库/权限测试 → 构建 → 关键端到端测试。上线前验证正式域名 HTTPS、认证回调地址与会话配置。

数据库迁移采用可追踪 SQL，先在测试库演练。对可能破坏现有数据的变更，先备份并设计前后兼容步骤，避免应用回滚后数据库已不兼容。

### 21.2 监控与备份

记录应用错误率、接口耗时、认证失败、导入失败和附件/数据库用量；不把私有颜色库内容作为分析事件上传。

数据库备份与应用层 JSON 导出各自保留，不能相互替代。选择部署方案后明确恢复点、恢复目标、保留策略和恢复负责人，并实际演练。

可选的“最常用颜色”统计优先使用账号内本地/私有计数；访客行为分析不是首版必需，默认不追踪跨站行为。

### 21.3 最终交付应包含

## 22. 关键风险与明确取舍

| 风险 | 决策与缓解 |
|---|---|
| “所有颜色相关功能都要做”导致无限扩张 | 首版只承诺收藏闭环；扩展走资源类型或工具模块 |
| 保存时统一转 HEX，造成丢精度或丢透明度 | 保存源空间、源通道、alpha 和高精度标准坐标 |
| 色块复制与点击详情冲突 | 色块只复制；标题和独立按钮进入详情 |
| 只用 localStorage，换浏览器数据就丢 | 服务器持久化；本地只作偏好和临时草稿 |
| 任意网址抓取导致 SSRF | 首版手动录入；P1 受控抓取器通过安全验收后启用 |
| 公开页面误带私有笔记或附件 | 分表、RLS、公开 DTO 和缓存隔离 |
| 过度承诺色觉友好或印刷准确性 | 检测结果带条件；ICC/专色能力不纳入首版 |
| 开源库升级改变颜色结果 | 锁版本、数值 fixture、保留源数据与引擎版本 |
| 第三方网站改变功能或阻止访问 | 外链书签始终可手动使用；不依赖未经确认的 API |
| 颜色推荐看起来漂亮但不可用 | 支持真实场景预览、角色分配和对比度检查 |
| 图片提色在设备间结果略有差异 | 记录处理条件；人工校正；不承诺跨设备绝对一致 |
| 前期引入过多基础设施 | 单应用、单数据库，按实际瓶颈扩展 |

**首版不设定社交点赞、交易、广告或收费会员。先验证个人收藏效率，再决定是否增加商业化和社区功能。**

## 最终实施建议

**先把“输入准确、展示准确、复制可靠、分类顺手、数据不丢、隐私不漏”六件事做扎实。**

之后通过相同的资源模型接入渐变、图片、文章和设计令牌，通过相同的颜色引擎接入转换、提色、预览和推荐。这样才能把个人收藏网站逐步扩展成颜色工作台，而不是一次做出很多看似丰富、实际上互不连通的小工具。
